🌱 BDD & Cucumber Fundamentals
Q1
What is BDD and how does Cucumber support it?
Conceptual
▼

Behavior-Driven Development (BDD) is an agile software development methodology where tests are written in plain English from the user's perspective before development begins. It bridges the gap between business stakeholders and developers.

Cucumber supports BDD by:

  • Allowing test scenarios to be written in Gherkin (a plain-English DSL)
  • Mapping those scenarios to step definitions written in Java, Ruby, JS, etc.
  • Making tests readable by non-technical stakeholders
  • Acting as living documentation for the application
Tip: Always mention that BDD promotes collaboration between Dev, QA, and Business (the "Three Amigos").
Q2
Explain the Gherkin syntax with all keywords.
Conceptual
▼

Gherkin is the language used to write Cucumber feature files. Core keywords:

  • Feature – High-level description of the functionality
  • Background – Steps common to all scenarios in the feature
  • Scenario – A specific test case
  • Scenario Outline – A template scenario with multiple data sets
  • Given – Sets the precondition
  • When – Describes the action/event
  • Then – Describes the expected outcome
  • And / But – Continuation of Given/When/Then
  • Examples – Data table used with Scenario Outline
  • @TagName – Adds metadata/tags to scenarios
  • """ – Doc Strings for multiline text
  • | – Data Tables inline with steps
Q3
What is the difference between Scenario and Scenario Outline?
Conceptual
▼

Scenario is a single test case with fixed data. Scenario Outline is a parameterized template that runs multiple times with different data sets supplied via the Examples table.

# Scenario Outline Example
Scenario Outline: Login with multiple credentials
  Given the user is on the login page
  When the user enters "<username>" and "<password>"
  Then the user should see "<message>"

  Examples:
    | username | password  | message        |
    | admin    | admin123  | Welcome Admin  |
    | user1    | pass456   | Welcome User   |
    | invalid  | wrong     | Login Failed   |
Tip: Scenario Outline reduces duplication. It's equivalent to data-driven testing.
Q4
What is the role of the Feature file and Step Definitions file?
Conceptual
▼

Feature File (.feature): Contains test scenarios written in Gherkin. It's the source of truth and acts as documentation. Readable by everyone on the team.

Step Definition File: Contains Java (or other language) methods annotated with @Given, @When, @Then that map to the Gherkin steps and contain the actual automation code.

// Step Definition
@Given("the user is on the login page")
public void userIsOnLoginPage() {
    driver.get("https://app.example.com/login");
}
🪝 Step Definitions & Hooks
Q5
What are Hooks in Cucumber? Explain @Before, @After, @BeforeStep, @AfterStep.
ConceptualPractical
▼

Hooks are code blocks that run at specific points during test execution:

  • @Before – Runs before each scenario (e.g., launch browser, set up DB)
  • @After – Runs after each scenario (e.g., close browser, clean DB)
  • @BeforeStep – Runs before each individual step
  • @AfterStep – Runs after each individual step (useful for screenshots)
  • @BeforeAll / @AfterAll – Run once before/after all scenarios (class-level)
@Before
public void setUp(Scenario scenario) {
    driver = new ChromeDriver();
    this.scenario = scenario;
}

@After
public void tearDown(Scenario scenario) {
    if (scenario.isFailed()) {
        byte[] screenshot = ((TakesScreenshot) driver).getScreenshotAs(OutputType.BYTES);
        scenario.attach(screenshot, "image/png", "Failure Screenshot");
    }
    driver.quit();
}
Q6
SCENARIO: You need to take a screenshot only when a test fails. How would you implement this in Cucumber?
Scenario-Based
▼

Use the @After hook and check scenario.isFailed():

@After
public void captureScreenshotOnFailure(Scenario scenario) {
    if (scenario.isFailed()) {
        TakesScreenshot ts = (TakesScreenshot) driver;
        byte[] screenshot = ts.getScreenshotAs(OutputType.BYTES);
        scenario.attach(screenshot, "image/png", scenario.getName());
    }
    driver.quit();
}
Tip: The Scenario object is automatically injected when declared as a parameter in the hook method.
Q7
SCENARIO: A @Before hook needs to run only for scenarios tagged @smoke. How do you do it?
Scenario-BasedPractical
▼

Pass the tag expression to the @Before annotation:

@Before("@smoke")
public void setupForSmoke() {
    System.out.println("Setting up smoke test environment...");
    driver = new ChromeDriver();
}

@Before("@regression and not @slow")
public void setupRegressionExcludingSlow() {
    driver = new FirefoxDriver();
}
Tip: Tag expressions support and, or, not operators since Cucumber 4+.
Q8
SCENARIO: You have a step definition that matches two Gherkin steps. What error occurs and how do you fix it?
Scenario-Based
▼

Cucumber throws an AmbiguousStepDefinitionException when more than one step definition matches a Gherkin step.

Fix:

  • Make the regex/expressions more specific
  • Use anchors: ^ (start) and $ (end) in regex patterns
  • Use Cucumber Expressions instead of regex where possible
// Ambiguous:
@Given("the user {string} logs in")
@Given("the user (.*) logs in")

// Fix: Use one consistent pattern
@Given("the user {string} logs in")
public void userLogsIn(String username) { ... }

How do you run a specific tagged test from the command line using Maven?
ConceptualPractical
▼ 
# Run only @smoke tagged scenarios
mvn test -Dcucumber.filter.tags="@smoke"

# Run @regression but not @slow
mvn test -Dcucumber.filter.tags="@regression and not @slow"

# Run @smoke OR @sanity
mvn test -Dcucumber.filter.tags="@smoke or @sanity"

Alternatively, configure in @CucumberOptions:

@CucumberOptions(
    features = "src/test/resources/features",
    glue = "stepDefinitions",
    tags = "@smoke",
    plugin = {"pretty", "html:target/cucumber-reports"}
)
Q10
SCENARIO: Your test suite has 200 scenarios. The CI pipeline must run only the critical path tests on every commit. How do you organize this?
Scenario-Based
▼

Strategy:

  • Tag critical scenarios with @critical or @smoke
  • Create a dedicated TestRunner class for CI with tags = "@critical"
  • In CI pipeline (Jenkins/GitHub Actions), run with -Dcucumber.filter.tags="@critical"
  • Full @regression suite runs nightly or on PR merge
# Jenkinsfile (Declarative Pipeline)
stage('Smoke Tests') {
    steps {
        sh 'mvn test -Dcucumber.filter.tags="@critical"'
    }
}
stage('Regression') {
    when { branch 'main' }
    steps {
        sh 'mvn test -Dcucumber.filter.tags="@regression"'
    }
}
Q11
SCENARIO: A particular test is flaky and should be temporarily skipped without deleting it. How do you handle it?
Scenario-BasedPractical
▼

Tag it with @ignore or @wip and exclude that tag during execution:

# In feature file
@regression @ignore
Scenario: Flaky payment timeout test
  Given ...

# In TestRunner or CLI
tags = "@regression and not @ignore"
Tip: Add a comment in the feature file explaining WHY it's ignored and reference the bug ticket number.
📊 Data Tables & Data-Driven Testing
Q12
What is the difference between DataTable and Scenario Outline with Examples?
ConceptualPractical
▼
  • DataTable: Passes structured data to a single step within a scenario. Good for bulk input (e.g., filling a form with many fields, or inserting multiple rows).
  • Scenario Outline + Examples: Runs the entire scenario multiple times with different input sets. Good for testing the same flow with varied data.
# DataTable usage
When the user registers with the following details:
  | firstName | lastName | email           |
  | John      | Doe      | john@email.com  |
  | Jane      | Smith    | jane@email.com  |

// Step Definition
@When("the user registers with the following details:")
public void registerUsers(DataTable dataTable) {
    List<Map<String, String>> users = dataTable.asMaps();
    for (Map<String, String> user : users) {
        String firstName = user.get("firstName");
        // ... fill form
    }
}

🏗️ Framework Design & POM Integration
Q15
How do you integrate Page Object Model (POM) with Cucumber?
ConceptualPractical
▼

POM separates UI interaction from test logic. In Cucumber, Page Objects are instantiated in Step Definition classes:

// Page Object
public class LoginPage {
    private WebDriver driver;

    @FindBy(id = "username") WebElement usernameField;
    @FindBy(id = "password") WebElement passwordField;
    @FindBy(id = "loginBtn") WebElement loginButton;

    public LoginPage(WebDriver driver) {
        this.driver = driver;
        PageFactory.initElements(driver, this);
    }

    public void login(String username, String password) {
        usernameField.sendKeys(username);
        passwordField.sendKeys(password);
        loginButton.click();
    }
}

// Step Definition
public class LoginSteps {
    private WebDriver driver = Hooks.driver;
    private LoginPage loginPage = new LoginPage(driver);

    @When("the user logs in with {string} and {string}")
    public void userLogsIn(String username, String password) {
        loginPage.login(username, password);
    }
}
Q16
SCENARIO: How do you share the WebDriver instance across multiple Step Definition classes in Cucumber?
Scenario-Based
▼

Use Dependency Injection (DI) via PicoContainer, Spring, or Guice. PicoContainer is the most common with Cucumber-Java:

// Shared context class
public class TestContext {
    private WebDriver driver;

    public WebDriver getDriver() {
        if (driver == null) {
            driver = new ChromeDriver();
        }
        return driver;
    }

    public void quitDriver() {
        if (driver != null) driver.quit();
    }
}

// Step Definition 1 - inject via constructor
public class LoginSteps {
    private TestContext context;
    public LoginSteps(TestContext context) {
        this.context = context;
    }

    @Given("user is on login page")
    public void openLogin() {
        context.getDriver().get("https://example.com/login");
    }
}

// Step Definition 2 - same TestContext instance injected
public class DashboardSteps {
    private TestContext context;
    public DashboardSteps(TestContext context) {
        this.context = context;
    }
}
Tip: PicoContainer is the go-to DI framework for Cucumber. Add cucumber-picocontainer dependency to pom.xml.

  @api @smoke
  Scenario: Retrieve user details successfully
    Given the API base URL is "https://api.example.com"
    And a valid auth token is available
    When a GET request is sent to "/users/101"

      | field    | value             |

@When("a GET request is sent to {string}")
public void sendGetRequest(String endpoint) {
    response = given()
        .header("Authorization", "Bearer " + token)
        .when()
        .get(baseURL + endpoint)
        .then()
        .extract().response();
}

@Then("the response status code should be {int}")
public void verifyStatusCode(int expectedCode) {
    Assert.assertEquals(response.getStatusCode(), expectedCode);
}

Store dynamic data in a shared context object injected via DI, or use a thread-safe ScenarioContext map:

// ScenarioContext utility
public class ScenarioContext {
    private Map<String, Object> contextMap = new HashMap<>();

    public void set(String key, Object value) { contextMap.put(key, value); }
    public Object get(String key) { return contextMap.get(key); }
}

// Step 1 - store generated order ID
@When("the user places an order")
public void placeOrder() {
    String orderId = orderPage.placeOrder();
    scenarioContext.set("orderId", orderId);
}

// Step 2 - retrieve order ID in the same scenario
@Then("the order should be visible in the system")
public void verifyOrder() {
    String orderId = (String) scenarioContext.get("orderId");
    Assert.assertTrue(adminPage.isOrderPresent(orderId));
}

SCENARIO: Your test needs to verify email delivery after user registration. How do you automate this?
Scenario-Based
▼

Use a mail testing service like Mailinator, MailHog, or GreenMail:

Scenario: Verify welcome email after registration
  Given the user registers with email "testuser+{timestamp}@mailinator.com"
  When the registration is successful
  Then a welcome email should arrive in "testuser+{timestamp}" inbox within 30 seconds
  And the email subject should be "Welcome to Our Platform!"
  And the email body should contain a "Verify Email" link
      
@Then("a welcome email should arrive in {string} inbox within {int} seconds")
public void verifyEmailArrived(String inbox, int timeout) {
    MailinatorClient client = new MailinatorClient("API_KEY");
    Inbox mailInbox = client.request(new GetInboxRequest(inbox));
    // Poll with retry logic up to timeout
    Assert.assertTrue(mailInbox.getMsgs().size() > 0);
}
Tip: For local environments, use MailHog (SMTP mock) and query its HTTP API in step definitions.

SCENARIO: Implement thread-safe WebDriver management for parallel Cucumber execution.
Scenario-BasedPractical
▼ 
public class DriverFactory {
    private static ThreadLocal<WebDriver> tlDriver = new ThreadLocal<>();

    public static WebDriver getDriver() {
        return tlDriver.get();
    }

    public static void setDriver(String browser) {
        WebDriver driver;
        switch (browser.toLowerCase()) {
            case "chrome": driver = new ChromeDriver(); break;
            case "firefox": driver = new FirefoxDriver(); break;
            default: throw new IllegalArgumentException("Unknown browser: " + browser);
        }
        tlDriver.set(driver);
    }

    public static void quitDriver() {
        if (tlDriver.get() != null) {
            tlDriver.get().quit();
            tlDriver.remove();
        }
    }
}
Q26
SCENARIO: A step definition works fine locally but fails in CI. The error is "element not found". What do you investigate?
Scenario-Based
▼

Typical causes and fixes:

  • Headless vs GUI: CI runs headless — some elements behave differently. Check browser window size: driver.manage().window().maximize()
  • Timing issues: CI machines are slower. Increase explicit waits or use WebDriverWait
  • Different browser version: Ensure ChromeDriver/browser versions match in CI
  • Stale elements: Re-find elements after page transitions
  • Environment config: Check if the URL/env in CI config.properties is correct
// Always use explicit waits over Thread.sleep()
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(15));
WebElement element = wait.until(
    ExpectedConditions.elementToBeClickable(By.id("submitBtn"))
);

📈 Reporting, CI/CD & Debugging
Q29
What reporting plugins are available in Cucumber? How do you generate HTML reports?
ConceptualPractical
▼

Configure in @CucumberOptions plugin array:

  • pretty – Colorized console output

Q30
SCENARIO: How do you re-run only the failed scenarios automatically after the first run?
Scenario-BasedPractical
▼

Use the rerun plugin to record failures, then create a second runner to re-run them:

// Runner 1 - Main Run
@CucumberOptions(
    features = "src/test/resources/features",
    glue = "stepDefinitions",
    plugin = {
        "rerun:target/rerun.txt",
        "html:target/reports/run1.html"
    }
)
public class TestRunner extends AbstractTestNGCucumberTests {}

// Runner 2 - Re-run failures
@CucumberOptions(
    features = "@target/rerun.txt",
    glue = "stepDefinitions",
    plugin = {"html:target/reports/rerun.html"}
)
public class RerunRunner extends AbstractTestNGCucumberTests {}
      
# Maven command to chain both runs
mvn test -Dtest=TestRunner || mvn test -Dtest=RerunRunner

SCENARIO: How would you implement retry logic for flaky steps in Cucumber?
Scenario-Based
▼

Use a custom retry mechanism or the Cucumber Retry plugin:

// Custom Retry Utility
public class RetryUtils {
    public static void retry(int maxAttempts, Runnable action) {
        int attempt = 0;
        while (attempt < maxAttempts) {
            try {
                action.run();
                return; // success
            } catch (Exception e) {
                attempt++;
                if (attempt == maxAttempts) throw new RuntimeException(e);
                try { Thread.sleep(1000 * attempt); } catch (InterruptedException ie) {}
            }
        }
    }
}

// Usage in Step Definition
@When("the payment is processed")
public void processPayment() {
    RetryUtils.retry(3, () -> {
        paymentPage.submitPayment();
        Assert.assertTrue(paymentPage.isSuccessVisible());
    });
}
Tip: For Cucumber 7+, use @Retry annotation with the cucumber-retry extension or configure in junit-platform.properties: cucumber.execution.retry.count=2

Q46
What are Cucumber Expressions vs Regular Expressions in step definitions?
Conceptual
▼

Cucumber Expressions are a simpler, more readable way to define step patterns (introduced in Cucumber 3+):

// Cucumber Expression (preferred)
@Given("the user has {int} items in the cart")
public void userHasItems(int count) { }

// With optional text
@When("the user click(s) the submit button")

// With alternation
@Then("the form is submitted/saved successfully")

// Named parameters
@Then("the response time is less than {long} milliseconds")

Regex is more powerful but harder to read:

@Given("^the user has (\\d+) items? in the cart$")
public void userHasItems(int count) { }
Tip: Prefer Cucumber Expressions. Use regex only when complex pattern matching is needed.

What is the Background keyword and when should you use it vs @Before hook?
Conceptual
▼
  • Background – Runs Gherkin steps before each scenario in the same feature file. Visible and readable in the feature file itself. Best for UI setup steps (navigating to a page, logging in).
  • @Before hook – Runs Java code before each scenario. Best for technical setup (launching browser, initializing objects, setting up DB).

What is a "Living Documentation" and how does Cucumber enable it?
Conceptual
▼

Living Documentation means the test specifications always reflect the current behavior of the system — they're never out of date because they ARE the tests.

Cucumber enables this by:

  • Writing tests in plain English (Gherkin) that serves as specification
  • If behavior changes, the tests fail → forcing documentation to be updated
  • Tools like Pickles, Serenity BDD, and Cucumber Reports generate browsable documentation from feature files
  • Feature files are stored in version control alongside code
