1 · What is an API and How Does It Work?

▼

An API (Application Programming Interface) is a contract that defines how two software systems communicate. In web development, a REST API exposes endpoints (URLs) that a client calls over HTTP to create, read, update, or delete data on a server.

CLIENT (Browser / Mobile App / Test Script) │ │ HTTP Request │ ┌──────────────────────────────────────────┐ │ │ Method: GET / POST / PUT / DELETE │ │ │ URL: https://api.example.com/users/1 │ │ │ Headers: Content-Type, Authorization │ │ │ Body: { "name": "Alice" } (if POST) │ │ └──────────────────────────────────────────┘ │ ▼ API SERVER (Express / Spring Boot / Django) │ │ Processes request → hits Database / Business Logic │ │ HTTP Response │ ┌──────────────────────────────────────────┐ │ │ Status: 200 OK / 201 Created / 404 … │ │ │ Headers: Content-Type: application/json │ │ │ Body: { "id": 1, "name": "Alice" } │ │ └──────────────────────────────────────────┘ │ ▼ CLIENT receives & parses response

Key concepts:

  • Endpoint – A specific URL that represents a resource, e.g. /api/users
  • HTTP Method – Describes the intended action (GET, POST, PUT, PATCH, DELETE)
  • Request Headers – Metadata sent with the request (Content-Type, Authorization, Accept)
  • Request Body – The payload sent with POST/PUT/PATCH (usually JSON or XML)
  • Response Status Code – A numeric code indicating success or failure
  • Response Body – The data returned by the server (JSON, XML, plain text)
  • Base URL – The common prefix for all endpoints, e.g. https://api.example.com/v1

4 · API Authentication – Complete Guide

▼

Authentication proves who you are. Authorization decides what you can do. Most APIs require both.

① Basic Authentication

Username and password are Base64-encoded and sent in the Authorization header. Simple but insecure over plain HTTP — always use HTTPS.

Authorization: Basic dXNlcjpwYXNzd29yZA==
# dXNlcjpwYXNzd29yZA== is Base64("user:password")

② API Key

A static secret token issued by the server. Can be sent as a header, query param, or in the body.

# As a header (preferred)
X-API-Key: a1b2c3d4e5f6

# As a query parameter (visible in logs — less secure)
GET https://api.example.com/data?api_key=a1b2c3d4e5f6

③ Bearer Token (OAuth 2.0 / JWT)

The most common method in modern APIs. The client first obtains a token via a login/auth endpoint, then sends it with every subsequent request.

CLIENT AUTH SERVER │ │ │── POST /auth/token ─────────────────▶│ │ { username, password, client_id } │ │ │ │◀── 200 OK ──────────────────────────│ │ { access_token: "eyJ...", expires_in: 3600 } │ │── GET /api/orders ──────────────────▶ RESOURCE SERVER │ Authorization: Bearer eyJ... │ │ │ │◀── 200 OK ────────────────────────── │ │ { orders: [...] }
# REST Assured – Bearer Token
given()
  .header("Authorization", "Bearer " + accessToken)
.when()
  .get("/api/orders")
.then()
  .statusCode(200);

④ JWT (JSON Web Token) – Structure

A JWT has three Base64URL-encoded parts separated by dots: header.payload.signature

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 ← Header (algo + type) . eyJzdWIiOiJ1c2VyMTIzIiwicm9sZSI6ImFkbWluIiwiZXhwIjoxNzA5MDAwMDAwfQ ← Payload (claims) . SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c ← Signature (verify integrity)
Key claims: sub (subject/user ID), exp (expiry timestamp), iat (issued at), role (custom claim). You can decode the header and payload at jwt.io — but never share a real token.

⑤ OAuth 2.0 – Client Credentials Flow (machine-to-machine)

# Step 1: Get token
POST /oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id=myClientId

&scope=read:orders

# Response
{ "access_token": "eyJ...", "token_type": "Bearer", "expires_in": 3600 }

# Step 2: Use token
GET /api/orders
Authorization: Bearer eyJ...

5 · REST Assured – The API Testing Library (Java)

▼

REST Assured is the most popular Java library for API testing. It provides a domain-specific language (DSL) following the Given / When / Then pattern.

// Maven dependency
<dependency>
  <groupId>io.rest-assured</groupId>
  <artifactId>rest-assured</artifactId>
  <version>5.4.0</version>
  <scope>test</scope>
</dependency>
import static io.restassured.RestAssured.*;
import static org.hamcrest.Matchers.*;

// Base URI setup (do once in @BeforeClass)
RestAssured.baseURI = "https://api.example.com/v1";

// GET request
given()
  .header("Authorization", "Bearer " + token)
  .queryParam("page", 1)
.when()
  .get("/users")
.then()
  .statusCode(200)
  .body("data.size()", greaterThan(0))
  .body("data[0].name", notNullValue());

// POST request
given()
  .contentType(ContentType.JSON)
  .header("Authorization", "Bearer " + token)
  .body("{ \"name\": \"Alice\", \"email\": \"alice@example.com\" }")
.when()
  .post("/users")
.then()
  .statusCode(201)
  .body("id", notNullValue())
  .body("name", equalTo("Alice"));
Structure: given() = request setup → when() = HTTP call → then() = assertions. This maps cleanly to BDD Given/When/Then.

6 · What to Test in Every API – Testing Checklist

▼

For every API endpoint, verify these dimensions:

  • Status Code – Correct code for the scenario (200, 201, 400, 401, 404…)
  • Response Schema – All required fields exist with correct data types
  • Response Values – Actual field values match expected data
  • Headers – Content-Type, Cache-Control, CORS headers are correct
  • Response Time – API responds within an acceptable SLA (e.g. under 2 seconds)
  • Authentication – 401 when no token, 403 when insufficient permissions
  • Validation Errors – 400/422 with meaningful error messages for bad input
  • Boundary Values – Empty strings, null, very long strings, negative numbers
  • Pagination – page, limit, total fields behave correctly
  • Idempotency – Calling GET/PUT/DELETE multiple times has the same result
  • Error Messages – Errors are descriptive but do not leak sensitive data

Q2
What is the difference between PUT and PATCH?
Conceptual
▼

PUT replaces the entire resource. If you omit a field it gets removed or set to null.

PATCH applies a partial update — only the fields you send are changed.

// Current resource: { "id": 1, "name": "Alice", "role": "admin" }

// PUT – replaces everything
PUT /users/1  →  { "name": "Bob" }
// Result:         { "id": 1, "name": "Bob", "role": null }  ← role lost!

// PATCH – partial update
PATCH /users/1  →  { "name": "Bob" }
// Result:           { "id": 1, "name": "Bob", "role": "admin" }  ← role preserved
Test tip: Always test PUT by omitting optional fields to ensure the server does not silently discard data from other clients.
Q3
What is an idempotent API call? Give examples.
Conceptual
▼

An API call is idempotent if making the same request once or multiple times produces the same server state.

  • GET /users/1 — always returns the same user; calling it 10 times changes nothing ✅
  • DELETE /users/1 — first call deletes; subsequent calls return 404 but the state is still "user deleted" ✅
  • PUT /users/1 { name: "Alice" } — calling it 5 times still results in name="Alice" ✅
  • POST /orders — each call creates a new order, so 5 calls = 5 orders ❌ (not idempotent)
Why it matters for testing: Non-idempotent endpoints (POST) need cleanup after each test run to avoid duplicate data.
Q4
What is the difference between Query Parameters and Path Parameters?
Conceptual
▼

Path Parameters identify a specific resource and are part of the URL path:

GET /users/{id}  →  GET /users/42  (fetches user with ID 42)

Query Parameters filter, sort, or paginate a collection and appear after ?:

GET /users?role=admin&page=2&limit=10

In REST Assured:

// Path parameter
given().pathParam("id", 42).when().get("/users/{id}");

// Query parameter
given().queryParam("role", "admin").queryParam("page", 2).when().get("/users");

Q6
How do you obtain and reuse a JWT token across all API tests in REST Assured?
PracticalAuth
▼

Fetch the token once in a @BeforeAll / base class setup and store it as a static field:

public class BaseTest {

    protected static String authToken;

    @BeforeAll
    static void getAuthToken() {
        authToken = given()
            .contentType(ContentType.JSON)
            .body("{ \"username\": \"admin\", \"password\": \"secret\" }")
        .when()
            .post("/auth/login")
        .then()
            .statusCode(200)
            .extract()
            .path("token");         // or "access_token" depending on API
    }
}

// Use in test:
given()
    .header("Authorization", "Bearer " + authToken)
.when()
    .get("/users")
.then()
    .statusCode(200);
Tip: Store the token as a static field so it is fetched once per test suite, not before every test. This keeps your suite fast.

Q8
SCENARIO: Your JWT token expires mid-test-run. How do you handle token refresh?
Scenario-BasedAuth
▼

Track the expiry time and re-fetch before it expires:

public class TokenManager {
    private static String token;
    private static long expiryTime;

    public static String getToken() {
        // Refresh 60 seconds before expiry
        if (token == null || System.currentTimeMillis() > expiryTime - 60_000) {
            Response response = given()
                .contentType(ContentType.JSON)
                .body("{ \"username\": \"admin\", \"password\": \"secret\" }")
            .when()
                .post("/auth/login");

            token      = response.path("access_token");
            int expiresIn = response.path("expires_in");  // seconds
            expiryTime = System.currentTimeMillis() + (expiresIn * 1000L);
        }
        return token;
    }
}
Tip: This pattern is called "lazy token refresh". Each test calls TokenManager.getToken() — it refreshes automatically when needed.

🎯 Scenario-Based Questions
Q14
SCENARIO: A GET /products API suddenly returns 503. What are the possible causes and how do you investigate?
Scenario-Based
▼

503 Service Unavailable means the server is temporarily unable to handle the request.

Possible causes:

  • The service/pod is down (check server logs, k8s pod status)
  • Database connection pool exhausted
  • Deployment in progress (rolling update, maintenance window)
  • Upstream dependency (cache, DB, microservice) is failing
  • Load balancer health check failing

Investigation steps:

  1. Check the Retry-After response header (server may tell you when to retry)
  2. Hit /health or /status endpoint — is it also failing?
  3. Check server/application logs for exceptions
  4. Check if the issue is environment-specific (works in staging but not prod?)
  5. Check monitoring dashboards (CPU, memory, DB connection count)
In tests: A 503 from a stable environment is a bug — raise it immediately. A 503 in CI may be a flaky environment, so add retry logic for infrastructure issues, not for application logic.
Q15
SCENARIO: A POST /orders API returns 200 instead of 201. Is this a bug?
Scenario-Based
▼

Technically yes — it violates REST conventions. 201 Created is the correct status for successful resource creation. Returning 200 is non-standard because:

  • 200 means "the request succeeded" — it doesn't convey that a new resource was created
  • 201 should also include a Location header pointing to the new resource URL
  • Clients and other services may rely on the 201 code to trigger downstream actions

However, in practice, many legacy APIs return 200 for POST. Your test should:

  1. Check the API contract/documentation — if it says 200, align your tests with the documented contract
  2. Raise a defect and link to RFC 7231 (HTTP semantics) as supporting evidence
  3. Never silently accept incorrect codes — document the deviation

SCENARIO: You need to test a DELETE endpoint but the test data gets deleted after the first run. How do you manage test data?
Scenario-Based
▼

Use the Create → Test → Cleanup pattern to make each test self-contained:

public class DeleteOrderTest {

    private static int orderId;

    @BeforeEach
    void createTestOrder() {
        // Create fresh test data before each test
        orderId = given()
            .header("Authorization", "Bearer " + authToken)
            .contentType(ContentType.JSON)
            .body("{ \"product\": \"Book\", \"qty\": 1 }")
        .when()
            .post("/orders")
        .then()
            .statusCode(201)
            .extract().path("id");
    }

    @Test
    void deleteOrder_shouldReturn204() {
        given()
            .header("Authorization", "Bearer " + authToken)
        .when()
            .delete("/orders/" + orderId)
        .then()
            .statusCode(204);
    }

    @Test
    void deleteOrder_calledTwice_shouldReturn404() {
        // First delete
        given().header("Authorization", "Bearer " + authToken)
               .when().delete("/orders/" + orderId).then().statusCode(204);
        // Second delete
        given().header("Authorization", "Bearer " + authToken)
               .when().delete("/orders/" + orderId).then().statusCode(404);
    }
}
Alternatives: Use a dedicated test DB that resets between runs, or use a mock server (WireMock) for complete isolation.

Q36
SCENARIO: A POST /checkout API returns 200 but the order is never saved in the database. How do you investigate?
Scenario-Based
▼

@Test
void concurrentOrders_shouldNotCreateDuplicates() throws Exception {
    String idempotencyKey = UUID.randomUUID().toString();
    int threadCount = 5;
    CountDownLatch latch = new CountDownLatch(threadCount);
    List<Integer> createdIds = Collections.synchronizedList(new ArrayList<>());

    for (int i = 0; i < threadCount; i++) {
        new Thread(() -> {
            try {
                int id = given()
                    .header("Authorization", "Bearer " + authToken)
                    .header("Idempotency-Key", idempotencyKey)  // RFC 7231
                    .contentType(ContentType.JSON)
                    .body(orderPayload)
                .when().post("/orders")
                .then().extract().path("id");
                createdIds.add(id);
            } finally { latch.countDown(); }
        }).start();
    }

    latch.await();
    // All 5 calls should return the same order ID
    assertThat(new HashSet<>(createdIds).size(), equalTo(1));
}
Fix: The server should support the Idempotency-Key header — store the key and return the same response for duplicate requests within a time window.

@Test
void cursorPagination_shouldIterateAllPages() {
    List<String> allIds = new ArrayList<>();
    String cursor = null;

    do {
        RequestSpecification req = given()
            .header("Authorization", "Bearer " + authToken)

        allIds.addAll(pageIds);

        cursor = response.path("pagination.next_cursor");  // null on last page

    } while (cursor != null);

    // No duplicate IDs across pages
    assertThat(allIds.size(), equalTo(new HashSet<>(allIds).size()));
    assertThat(allIds.size(), greaterThan(0));
}

Q48
SCENARIO: The API team says "we don't need to test headers". How do you convince them otherwise?
Scenario-Based
▼

Response headers carry critical non-body information. Here's what headers tell you that body content doesn't:

  • Content-Type — if this is wrong, the client may misparse the body (e.g. parse JSON as text)
  • Cache-Control / Expires — wrong values cause clients to cache sensitive or stale data
  • Access-Control-Allow-Origin (CORS) — wrong value causes browser clients to reject the response
  • X-Content-Type-Options: nosniff — security header preventing MIME sniffing attacks
  • Strict-Transport-Security — enforces HTTPS; missing = MITM attack risk
  • Location — must be present on 201 Created to point to the new resource
  • Retry-After — must be present on 429 to tell clients when to retry
// Header assertions in REST Assured
.then()
    .header("Content-Type",               containsString("application/json"))
    .header("X-Content-Type-Options",     equalTo("nosniff"))
    .header("Cache-Control",              containsString("no-store"))  // for auth endpoints
    .header("Access-Control-Allow-Origin", notNullValue());

SCENARIO: How do you test an API that uses server-sent events (SSE) or long polling for real-time updates?
Scenario-Based
▼

SSE and long polling keep the HTTP connection open and stream data over time. REST Assured isn't ideal for streaming; use OkHttp or specific SSE libraries:

// Testing SSE with OkHttp
@Test
void sse_orderUpdates_shouldReceiveStatusChange() throws Exception {
    OkHttpClient client = new OkHttpClient.Builder()
        .readTimeout(30, TimeUnit.SECONDS).build();

    Request request = new Request.Builder()
        .url(baseUrl + "/orders/42/stream")
        .header("Authorization", "Bearer " + authToken)
        .header("Accept", "text/event-stream")
        .build();

    List<String> receivedEvents = new ArrayList<>();
    CountDownLatch latch = new CountDownLatch(1);

    try (Response response = client.newCall(request).execute()) {
        assertThat(response.code(), equalTo(200));
        assertThat(response.header("Content-Type"), containsString("text/event-stream"));

        BufferedSource source = response.body().source();
        while (!source.exhausted()) {
            String line = source.readUtf8Line();
            if (line != null && line.startsWith("data:")) {
                receivedEvents.add(line.replace("data:", "").trim());
                if (receivedEvents.size() >= 1) { latch.countDown(); break; }
            }
        }
    }

    latch.await(10, SECONDS);
    assertThat(receivedEvents, not(empty()));
}
Q59
SCENARIO: How do you prioritize which API test cases to automate first when you have limited time?
Scenario-BasedConceptual
▼

Prioritize by risk × value:

  1. Core happy paths — the endpoints that 80% of users hit every day (login, create order, fetch products)
  2. Authentication & authorization — security bugs have the highest business impact
  3. Data-modifying endpoints — POST, PUT, DELETE have more risk than GET
  4. Previously defective areas — wherever bugs were found before, regression risk is highest
  5. Integrations with third parties — payment, email, SMS — these are high-risk and hard to test manually
  6. Contract / schema validation — run on every endpoint; cheap to write, catches regressions early
  7. Negative / boundary cases for critical fields — price, quantity, ID fields where bad data causes financial damage
Leave for last: Edge cases on non-critical read endpoints, formatting tests, and tests that require complex setup with low coverage value.
